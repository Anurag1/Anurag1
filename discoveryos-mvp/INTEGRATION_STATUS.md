This document distinguishes a working local prototype from proposed integrations.

| Component | Role in DiscoveryOS | Current integration status | Next interface |
|---|---|---|---|
| HONet-Lifelong-Learning | Continual-learning experiments | Adapter contract only; no runtime import | Export task metrics, task IDs, and checkpoint metadata as JSON |
| Generalised-Meta-Attention-Architecture | Self-critique / confidence / reasoning | Adapter contract only; no runtime import | Export critique, confidence, assumptions, and rule candidates as JSON |
| SUPHAI_MODEL | Multi-agent coordination | Adapter contract only; no runtime import | Export task, agent, status, output, and evidence references as JSON |
| Prometheus-AGI | State comparison / hypothesis loop | Adapter contract only; no runtime import | Export previous state, observed changes, hypotheses, and persisted results |
| DiscoveryOS MVP | Evidence ledger, graph, lexical contradiction triage | Implemented as standalone Python package | Consume normalized component exports |

## Why JSON contracts first?

The repositories are not currently one shared installable package. Importing arbitrary files across projects would hide dependency and runtime assumptions. The adapter boundary makes data provenance explicit and enables components to be connected one at a time.

## Completion criteria for true integration

1. At least one real component emits an export from its own runtime.
2. DiscoveryOS ingests it without hand-editing the exported data.
3. The source run/configuration is retained for traceability.
4. CI tests the adapter against a checked-in fixture generated by that component.
5. An end-to-end benchmark compares the integrated system with baselines on identical cases.

Until those criteria are met, the component registry is a declared interface contract, not proof that all modules are connected.
